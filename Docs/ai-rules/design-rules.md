# 设计文档的写法

给 AI 看。人读的是 [设计文档](../design.md)，这份写改它时守什么规矩。改设计文档前先读这份。

## 读者

设计文档给人看：作者本人、作品集的老师、做 video essay 时回看流程。读者懂游戏，但不看代码，也不关心引擎里怎么搭。

## 写什么

- 玩法：玩家能做什么、按什么键、系统之间怎么配合。
- 关卡流程：每关的起点、终点、步骤、完成条件、本关物品。
- 叙事：每一步玩家知道了什么、感受到什么，为什么这样安排。
- 美术需求：要做哪些资源、各自用在哪。
- 待定的地方标 **待定**，还在想的标 **构想**。

## 不写什么

- 实现现状和进度，比如“已实现”“已放进场景”“还没接入”。
- 脚本名、组件名、场景对象路径、存档键、JSON 字段、参数数值。
- 交互的实现细节：取景框颜色、印章和相框样式、拖拽预览、放不下的边界判定、文字逐字速度、点击加速和继续箭头、画幅比例、动效时长。
- 修改经过，比如“原来是”“某日改为”。
- 提示和内心独白的正文：只写编号，链接到 `json-hints.md`、`json-inner-monologue.md`；F 交互提示链接到 `game-text.md`。

判断方法：一句话如果换一种做法实现就得跟着改，它就不属于设计文档。写玩家看到什么、感受到什么，不写它是怎么做出来的。

## 细节放哪

| 内容 | 放在 |
| --- | --- |
| 系统规则、交互细节、判定条件、已实现和待实现 | `Docs/Specs/Systems/` 下对应的系统 Spec |
| 某一关的实现清单、测试入口 | `Docs/Specs/Levels/` 下对应的关卡 Spec |
| 场景对象、资源、参数、注意事项 | 对应目录的 CLAUDE.md |
| 游戏里显示的文字 | `json-` 文档和 `game-text.md` |
| 改了什么、为什么 | `development-log.md` |

从设计文档里删细节前，先确认对应的 Spec 或 CLAUDE.md 里已经有；没有就先补进去再删。

## 改设计时

- 设计变了要同步实现时，只改设计本身，不在设计文档里注明实现进度；实现状态写进对应 Spec。
- 设计改动影响剧本时同步 `script.md`，影响游戏文字时同步对应 `json-` 文档和 `game-text.md`。
- 写完通读一遍改动的段落，确认读者不看代码也能看懂。
